# Grok law review: --threads

The drafted `law threads` does not say that `N` leaves the output unchanged. It should be rejected until the statement covers every position where the parser expects an option.

1. **Blocker.** `law threads` in the `MACHINE.bend` diff in `notes/threads.md` (the clause `launch(Norm.start("norm" <> "--threads" <> x <> rest), ...)`). The two command lines differ only by a `--threads N` placed immediately after `norm`. Any later `--threads` sits in `rest` on both sides, so the equality stays true while that later `N` still changes the header or the result. The line a user writes, `norm -f ref.fa --threads N in.vcf`, and the same flag after the VCF path, are outside the law. Transitivity ("the same as any other `N`") reaches only that one position. `law machine` does not close the hole: it ties each command line to `L.run` of its own `Cfg`, and nothing says those `Cfg`s match once the flag moves. The usage case is fine as written. When `rest` does not parse, both sides are `Norm.Usage{}` and `launch` is `None{}`; if a valid `N` turned a bad command into a successful one, the law would fail.

   **Fix.** Keep a launch equality, and quantify the insertion point. With `Args.expecting(pre)` meaning `Args.go(pre, Args.init())` is still `PNone` and `ok`:

   `launch` of `norm <> pre <> ["--threads", x] <> post` equals `launch` of `norm <> pre <> post`, under `Pos.read(x) == Some{n}`, `1 <= n <= Args.max_threads()`, `Args.expecting(pre)`, and the same `hf`, `h`, and `hb` as now (`hb` on the longer command line). `texts_ok` is per word and per piece (`MACHINE.bend`), and the extra words are `"--threads"` and digits, so the longer command being bytes covers the shorter one. `pre` empty is today's statement. One `N` equals the command without it, so two values of `N` agree at every option position, including after the VCF path. The word after `-f`, `-c`, `-w`, or `--threads` has `pend` set, `expecting` is false, and the law stays silent there. The comment should say paths, stdout bytes, messages, and exit code. Worker count is not in this law.

2. **Should fix.** `Args.threads` and `Args.thr` in the `types.bend` diff. `Args.thr` stores `Some{n}` for `0` and for `129` and only then clears `ok`. `Args.threads` returns that `Some` without checking `norm`, `ok`, or `pend`. On `norm --threads 4 --threads` the state is still `ok` with `pend = PThr`, `parse` is `None`, and `threads` is `Some{4}`. On `norm --threads 129 -f r.fa in.vcf` it is `Some{129}`. The comment says the result is that `N` or `None`. The driver is told to size its arrays from this function, and the arrays have 128 slots.

   **Fix.** Return `Some{n}` only for a command `Args.parse` accepts. Then `n` is in `1..128`. Every rejected command, including a bad or missing value and a first word other than `norm`, is `None`.

3. **Minor.** `args_threads_mid` and `args_threads_path` in the `examples.bend` diff. Both lock `parse` and the recorded words. Neither locks `Args.threads`: `"008"` should be `Some{8}`, and `-f --threads` as a path should be `None`.

The grammar is unambiguous, and a command line that never uses the option has the same `Cfg` as today, including `Opts.args`. The `PThr` arm runs only for the exact word `--threads` while no value is pending. Every other word is appended to `keep` once, in order, and `strict`, `w`, the paths, and `ok` follow the old rules, so `keep` is `rest`. That covers `args_ok`, `args_default`, `args_w0`, `args_two_vcf`, and `args_no_ref`. `-f --threads` is a path, and `args_threads_path` is right. `-c --threads` and `-w --threads` are bad values, so `parse` is `None`, as today. A missing value leaves `pend = PThr`, so `Args.done` is `None`; `args_threads_end` is right. `--threads=8` is not the option. The last in-range value wins. `0`, `129`, and a non-number are `None` by `law usage` once `parse` refuses them. Those corners belong in the examples, not in a new law.

The five questions:

1. Leave `--threads` and its value out of `Opts.args`. The launch equality can then be exact, which is the property worth proving. The header already drops the date so the file is the same on every machine. `N` is not part of the result. `-c`, `-w`, and the paths stay on `##framebender_normCommand`.
2. Keep `1..128`, and keep `0` a usage error. `128` is Bend's worker cap and the size of the driver's arrays. Above that, one flag means reading the whole VCF ahead. `0` meaning "default" would mean batch `16`. In bcftools, `0` means no extra threads, which here would be `1`. A usage error is the reading that does not pick one of those quietly.
3. State every position where an option is expected, as in finding 1. "Right after `norm`" leaves the command users write outside the contract. Naming `Args.expecting(pre)` keeps `ArgSt` out of the law text.
4. Leave the parser fact a lemma in the proof of that law. Do not add it to `LAWS.bend`. That file is the normalization science. A front-only lemma is enough only for the law as drafted. It is not enough for the law in finding 1, which is the point of making the statement general.
5. Set the runtime's thread count from the `io64.c` constructor through `BENDRTS`. One flag then sizes the batch, the read-ahead, the reference reads in flight, and the workers. `+RTS --threads N -RTS` sizes only the workers. The constructor is trusted driver code. If its scan and `Args.parse` ever disagree, only the worker count changes. A user's own `BENDRTS` or `+RTS` may win. The law should stay silent on that. The constructor belongs to the driver review.
