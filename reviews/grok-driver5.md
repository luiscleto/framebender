# Grok driver review 5 (Grok, plan mode)

ACCEPT.

1. Threads writing heap blocks. Safe on this runtime. A helper writes only the payload of a block the main thread allocated and still owns. A FASTA block is read or freed only after `pthread_join`. A read-ahead block is read only after the helper publishes it as full under the mutex, and that slot is not reused until the main thread has taken it. There is no moving collector. `corpus_grow` relocates bank storage only, under `bank_lock`, which the helpers never take. This is the accepted one-block read-ahead, now for up to 16 VCF blocks and 32 FASTA blocks.

2. Ticket invariant. No path starts a 33rd read before a wait. `answers` groups by 32, starts that group, waits it out, then starts the next. An unknown contig, an empty span, and a span over 2^31 take no ticket. This machine asks at most 32 reads (16 pieces, two each). A `die` during `waits` leaves the later tickets pending and the process exits. The ticket-32 `EINVAL` path is idle for this driver.

3. Error order. The first failure in Ask order is the one reported. `waits` walks the list head-first, `die` stops the process, and errno is taken before the layout code. A slow short index (code 2) and a fast illegal byte (code 1) in one Ask match the previous driver in both orders, including a 16-piece batch on the piece-size-1000 build: `.fai index does not match` when the short index is first, `unsupported FASTA` when the space is first. Exit code 2.

4. Read-ahead ring. Pieces stay in order. The hand-out is the head slot under the mutex. A short or failed piece is that piece, and it ends the helper. On a device heap miss, `give` stops adding blocks. An empty queue ends the helper and the caller reads the piece itself. Pieces already queued are kept. A stream switch joins the helper and returns `EBUSY` if a filled piece was never taken. The driver uses one piece size, so the `EINVAL` check stays idle. Plain, `-c e`, `-c w`, real BGZF, plain gzip, a damaged block, and a file cut after the first BGZF block all match the previous driver in stdout, stderr, and exit code. `bend main.bend -o` matches `build.sh` on plain input and reports `no BGZF in this build` on `.vcf.gz`.

5. Pipe or FIFO. An early stop still exits while the helper is blocked in `read`. `File.close` only closes the descriptor. `IO.exit` is `fflush` then `exit()`, which ends the whole process. Checked with the real binaries: a VCF of exactly 16 pieces (58,720,256 bytes), first record a real `REF_MISMATCH`, writer never closing. Pipe and FIFO, `-c e`: both drivers exit 1 with `error: REF_MISMATCH	c	1	line 3` and identical stdout and stderr. The same pipe with a FASTA whose first base is a space, `-c w`: both exit 2 with `error: unsupported FASTA`. A writer that supplies 1000 bytes and never closes leaves both drivers waiting, because the first piece is not full and there is no EOF.

6. Memory. The extra memory is the 16 queued pieces and the 32 buffers of 1 MiB. That matches the machine's batch. I would leave the ring at 16.

7. Out of memory. On a CPU build a heap block that cannot be allocated never becomes the driver's `out of memory`. `heap_alloc_miss` calls `err_fail` and `_exit(1)` with `bend: out of memory` before `io64_block` returns, including on a later `fa_start` while an earlier read has not been waited. The law allows that runtime stop. A failed `malloc` of the 1 MiB bounce buffer sets `ENOMEM` on that read and is reported at its wait, in order. On a device build `io64_block` still returns failure, and the driver reports `out of memory` at that wait.
